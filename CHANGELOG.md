# Changelog

Formato basado en [Keep a Changelog](https://keepachangelog.com/es-ES/1.1.0/). Cada PR agrega su entrada bajo `[Unreleased]`; no se crean archivos nuevos en `docs/` para cambios puntuales (ver `CLAUDE.md`).

## [Unreleased]

### Added

- La calculadora de barriles ahora tiene arquitectura viewport-first: layout reutilizable de módulo interactivo, flujo mobile por pasos, modales compactos para estilos y mezcla, y tests de duración extendida/selección múltiple/porcentajes.
- Opción para editar manualmente la cantidad de litros de cerveza por persona en la calculadora de barriles.
- `lib/db/src/schema` ahora define en Drizzle las 9 tablas del esquema comercial/admin (antes vacío), espejando `supabase/migrations/20260725120000_commercial_admin_foundation.sql` (columnas, checks, únicos, FK). No se tocaron endpoints de `api-server`; el frontend sigue consultando Supabase directamente.
- Se agregó infraestructura de tests (vitest) a `lib/db` y `artifacts/api-server`, antes sin ningún test: sanity checks del esquema recién portado y de sus `insertXSchema` (drizzle-zod), y un test del endpoint `GET /api/healthz` con `supertest`.
- Se integró Sentry (`@sentry/react`) para error tracking en producción. Antes, los errores de render (`ErrorBoundary`), los fallos de Supabase al armar el catálogo comercial (`CommercialDataContext`), la verificación de rol admin (`AdminAuthContext`) y las mutaciones del panel admin (`useAdminDashboardData`) solo se registraban con `console.*` gateado a `DEV`, así que en producción quedaban invisibles para el equipo. Nuevo módulo `src/lib/monitoring/` (`config.ts` + `sentry.ts`) sigue el mismo patrón de configuración con degradación elegante que `lib/supabase/config.ts`: sin `VITE_SENTRY_DSN` o fuera de producción, `reportError()` es un no-op. El SDK va en su propio chunk de Vite (`vendor-sentry`) para no engordar el bundle principal, y la CSP de `vercel.json` ahora permite el host de ingest de Sentry en `connect-src`.
- Se cerraron las brechas de documentación que quedaban abiertas en `docs/code-audit-checklist.md` (secciones Documentación, CI/CD y Logging): nuevo `artifacts/lupulados/README.md` (env vars requeridas y comportamiento real vs. fallback estático de Supabase), nuevo `docs/obsidian-pending/README.md` que documenta el estado real de cada nota migrada de Obsidian (5 resueltas, 1 con QA manual pendiente), y dos secciones nuevas en `CLAUDE.md` ("Deploy": Vercel vía integración nativa de Git; "Política de logging": reglas sobre `console.*` gateado a `DEV` y uso de `reportError()`). El checklist de auditoría se actualizó para reflejar estos cambios.
- Se agregó infraestructura de testing de componentes a `artifacts/lupulados` (antes solo `vitest` en `environment: "node"`, sin DOM ni forma de renderizar/interactuar con componentes reales): `jsdom` + `@testing-library/react`/`jest-dom`/`user-event`, con `vitest.config.mjs` dividido en `test.projects` (`node` para los 36 specs de dominio existentes, `jsdom` + `setupFiles: src/test/setupTests.ts` para los nuevos `.test.tsx`) — sin tocar el comportamiento de los tests existentes. Se agregaron tests de integración con render real para los 3 flujos de mayor riesgo de negocio identificados en el audit: `Calculadora.test.tsx` (cálculo en vivo de la recomendación + callback `onUseRecommendation`), `ArmaTuPedido.test.tsx` (wizard completo de 5 pasos hasta el link de WhatsApp generado, verificado por su `href`) y `AdminLogin.test.tsx`/`AdminDashboard.test.tsx` (login + CRUD de productos), estos últimos mockeando `@/lib/supabase/client` y `@/lib/supabase/config` con un fake client reusable (`src/test/supabaseAdminMock.ts`) que imita el query builder encadenable de Supabase, siguiendo el único precedente de mock de módulo del repo (`sentry.test.ts`). Se agregó `@vitest/coverage-v8` con un gate de cobertura del 70% (statements/branches/functions/lines) acotado a `src/domain/**` (`coverage.include`), corrido en CI y en `.husky/pre-push` vía un nuevo script `test:coverage` que reemplaza a `test` en ambos (el `test` sin cobertura se mantiene para iteración rápida local). Playwright/E2E queda explícitamente fuera de alcance de este cambio — ver `docs/code-audit-checklist.md`.
